# HouseMate product specification

Status: evolving product scope  
Last updated: 2026-10-03

## Production reliability

Production integrates optional Sentry reporting for API and browser/server errors,
with household/request data, tokens and raw exception text removed before sending.
Operators configure separate project DSNs and issue alerts. HTTP uptime checks
cover the public web page and bounded read-only API database readiness, with owner
failure/recovery alerts. Financial writes retain their existing confirmation and
idempotency behavior during incidents. Encrypted logical backups include household,
Auth and Storage metadata; restore drills validate isolated data/API recovery.
Offsite retention and unattended backups require operator setup. A local drill
does not establish Supabase Auth delivery or production cutover acceptance.

## Product goal

HouseMate helps people sharing a home coordinate money and daily life in one place. Members should be able to see what they owe, what needs attention, and what changed without reconstructing decisions from chat messages or spreadsheets.

This document describes intended features and user-visible behavior. It can change as the product is tested. `AGENTS.md` holds the stable project boundaries, while `README.md` explains the current implementation and how to run it. The older product and domain documents in this folder provide detail; this SPEC takes precedence when their release scope or product choices conflict.

## First usable release

Notifications, Theme and Account stay at the right with 8px spacing. Notifications and Theme use plain icons without circular backgrounds or borders. Account and Search retain soft theme-aware circular backgrounds. Search is icon-only with an accessible label/shortcut tooltip; its dialog input has one shared focus outline. Theme switches between moon and sun. Account uses a person icon; the member's initial/name/email remain inside its menu. Notification unread badges stay within the control's corner. Phone headers retain at least 16px side padding plus safe-area insets, and use a fixed two-column header at widths up to 900px. Phone widths up to 650px show the mascot without the wordmark, keeping the logo/search on the left and other controls on the right in one row without shrinking 44px touch targets. In the installed phone app at widths up to 650px, Search uses a plain magnifying-glass icon with a transparent background to match Notifications and Theme; the 44px touch area and visible keyboard focus remain. Phone and desktop browser views retain the circular Search background.
- The navigation sidebar has no bottom profile block; account controls remain beside the top-bar theme toggle. A compact household row shows a small green initial badge, the household name and a chevron, without an uppercase caption or filled outer card. Its working menu shows the current household checked, other memberships, Create household, Join with invite and Household settings. Home has no separate household selector. At small-screen widths, the same control belongs to the global header area and opens a modal bottom sheet with safe-area padding. Switching retains the current tab/view and clears old record/create/event-prefill links. Switching/create/join/settings navigation requires finishing or discarding open drafts. Join validates an invite link/code and opens the existing invitation review before acceptance; creating another household retains existing memberships. Settings link to the selected household and retain normal role permissions. Preview disables real create/join actions.

- The Assistant's smiling house mascot is HouseMate's shared logo across navigation, sign-in and the public landing page, alongside the existing wordmark. The same character appears in browser, Android and iPhone app icons, using forest green, a pale background and a gold sparkle. The mobile header mascot uses a non-shrinking 44px tile to match the header controls. The Assistant's chat-focused layout is retained. In the signed-in workspace, the mascot is a keyboard-accessible refresh button with a minimum 44px touch target. Clicking or tapping it reloads the current page while preserving its URL and selected household. Open drafts and unsaved settings disable this refresh until finished or discarded; brand marks outside the workspace remain decorative.

### Household and members

- Sign in with Google or an email link, edit a display name, and create or join a household through a single-use shareable invitation link that expires after seven days.
- A household has an owner, optional admins, and members. Members see only households they belong to; role-appropriate controls are clear in the interface.
- Owners and admins may create and revoke invitations and edit household name and timezone. Only the owner may promote or demote admins; the owner role cannot be changed in this flow.
- Choose the household's currency and timezone at creation. The owner may change currency before the first confirmed financial record or saved shopping price; afterward it is read-only. Show household settings and membership status.
- Show a dashboard with balances, pending bills, meals, shopping, chores, events, and important recent activity as each feature becomes available.

### Household search

- A global Search control opens a focused modal on desktop and a safe-area-aware phone dialog. Ctrl/Command + K opens search unless another dialog is active. The input supports IME composition, debounces for 300 ms after at least two characters, and offers All records or one record type. Search is only available for a signed-in household, not sample preview data.
- The search panel starts compact, with a Search heading, small household label, prominent focused input and compact record-type selector. Clear search returns focus to the input and removes prior results. The two-character hint appears only for a one-character term. Result rows have category icons, titles, one-line previews, current state and subtle dates; keyboard arrows navigate rows. The desktop panel expands with results within a bounded height. On phones it is a bottom sheet with fixed input/filter controls above scrolling results, safe-area padding and visual-viewport positioning to stay above the keyboard. Initial empty panels omit the large illustration and repeated explanatory text.
- The current web search selector and All records results include only expenses, bills, manual transfers, events and announcements. Meals, chores, shopping and polls are excluded from every displayed result page. API search remains an authoritative, read-only operation with earlier record support for compatible clients. It matches case-insensitive literal substrings in titles and descriptive text (including providers, transfer names/method/notes, meal types, event locations and poll options). Queries accept 2–120 trimmed characters. No regex/wildcard operators, fuzzy matching, AI calls, email search, draft search or financial history-event search are included. When an API page contains only excluded records, web search retains Load more if another page exists.
- Results show type, title, bounded text preview, current state and creation/publication date, newest added first with deterministic ties. All saved states are searchable, including voided financial records, completed/cancelled items, past events/meals and expired/closed communications. Selecting a result opens the normal record detail; that endpoint checks access again. Open drafts must be finished/discarded before result navigation.
- Every page requires active household membership and applies announcement/poll audience/author/owner/admin rules before matching or pagination. No inaccessible results/counts are exposed. Default page size is 20, maximum 50, with a cursor scoped to the verified caller, household, normalized query and type. PostgreSQL microsecond ties are preserved; reads across pages are live, not a frozen snapshot. A bounded database timeout returns a safe, retryable error.
- Queries/results remain in tab memory while the dialog is open; no search history is written to URL, browser storage, analytics or provider prompts. Close, new query/filter, household/account change and disconnection clear prior results. Aborted/late responses cannot repopulate another query or scope. Reconnection searches again; temporary pagination failures allow retry, access failures clear retained results. Private API responses are no-store and never queued/cached offline.

### Profile and preferences

- Profile has a compact avatar/name/household/role header and three keyboard-accessible sections: My profile, Household and Preferences. The initial avatar uses the shared green accent palette in both light and dark themes. Only one section is shown at a time, including on phones and in the read-only design preview.
- Personal and household details start as saved summaries. Edit opens a form with Save and Cancel; Save requires a meaningful change. Failed saves retain the draft. Unsaved edits, pending role reviews and in-flight operations protect section changes, normal navigation links, household/account changes and reload/update prompts. Cancel restores saved values and does not write. Browser back/forward and forced termination are not persistent draft recovery.
- Account email appears inside expandable account details. Account switching and sign-out use the existing session flow. Members are listed by avatar/name/role without email in the main list. Owners explicitly review and confirm admin/member role changes; owner roles remain fixed. Owners/admins can edit household name/timezone; timezone search narrows a supported-value selector. Currency changes retain the existing owner-only and financial-activity restrictions.
- Household invitations show active links first with expiry and explicit creation/revocation; used, revoked and expired links are behind Show history. Create/join/switch actions live in the global household menu; invitation acceptance retains its existing review. Household settings links open the Household section from other routes or from Profile itself.
- Preferences offers the shared light/dark toggle, a household-scoped link directly to the existing notification settings (including actual push availability), and existing platform installation help/status. No additional notification subscription or permission is requested by opening Preferences.

### Home dashboard

- Home has no manual Refresh button. Keep the checked/update status and automatic API refresh on return, reconnection and the existing visible-tab polling interval; refresh failures explain automatic recovery.

- Home puts up to three earliest Unpaid bills first in Bills to watch. Bills remain ordered by due date; overdue means before today in the household timezone and due soon means today through seven days ahead, inclusive. Home no longer promotes chores, meals or shopping.
- Follow with two compact summaries: the signed-in member's confirmed net balance and the household's total Unpaid bills. Amounts use the household currency; voided bills are excluded. Include all pending bills in totals even when only three are previewed. Unpaid bills affect balances only when marked Paid.
- Show the three most recent financial events initially, with an option to expand to the ten returned by the API. Recent activity includes creation, edits, voids, provider-status changes, and reported manual transfers, newest first. Each entry opens the specific expense, bill, or transfer; record history shows prior values. Home has no quick-action button group; creation actions are available in their Money and House sections.
- Show loading, genuine empty results, errors with automatic-refresh guidance, and a last-updated time. Refresh on return to Home, window focus, reconnection, and roughly every minute while visible. Keep the last successful snapshot during temporary errors, visibly marked as possibly out of date; discard it on an access failure or household change.
- Events and announcements are not part of the Home summary. Do not invent counts or sample records as live data.

### Money, bills, and settlements

- Money opens on Balances and uses one shared header with the signed-in member's confirmed balance and the household's unpaid-bill total. The header omits the household currency badge; amounts still display their currency. Expenses and Bills remain separate sections with section-specific add actions. Their record lists and details sit side by side on desktop; on small screens, selecting a record focuses its detail with a Back control to return to the list. Bill/expense history previews three records in existing API date order; text-only View all bills/expenses and Show less controls expand/collapse the loaded list inside the same card, with Load more available while expanded. Details use text-only Hide details/View details controls, remain mounted while hidden, and reopen when selecting a record or following a direct link. Do not present household unpaid bills as the signed-in member's personal debt.
- Record an expense or bill with a payer, amount, date, description, participants, and split method. Preview each person's share before confirmation.
- Support equal, exact amount, percentage, ratio, selected-participant, and hybrid splits. Hybrid bills include individual charges, shared adjustments, credits or deductions, and a shared remainder. Ask the user to classify ambiguous adjustments.
- In the first bill flow, the shared remainder is split equally among selected active members. Each extra amount must be classified as a charge or credit for one member or a selected group. If an amount is outside the household, enter a household-only bill total before preview. The preview shows the base amount, every adjustment, and final shares that exactly total the household bill. An unassigned or ambiguous amount cannot be confirmed.
- The bill form presents Details, Split and adjustments, and Review in sequence. Details must be valid before moving to the split step; charges and credits are added only when needed. Review displays the API-calculated allocation and is the only step that can confirm the bill. Returning to edit a field invalidates the old preview.
- A bill has a type, provider, billing period, due date, and one manually recorded **Unpaid/Paid** status for payment to the provider. Any active member may update that status; HouseMate records the change but does not process a payment. Per-member repayments belong to the later settlement flow.
- Show each member's net balance and the confirmed expenses, Paid bills, and recorded transfers behind it. Why this balance and Recorded transfers initially show three records in source/transfer date order; text-only View all sources/transfers and Show less controls expand/collapse the loaded list inside each card, with pagination available while expanded. Suggested transfers initially shows two entries in API order with independent View all suggestions/Show less controls. These controls do not open separate pages, dialogs or panels, and have no dropdown arrows. Changing the selected member resets the source preview. A positive balance is owed to that member; a negative balance is what they owe. Unpaid bills appear as pending and affect balances only when marked Paid.
- Show settlement suggestions as informational amounts, separate from the history of transfers members have recorded. Preview the first two current suggestions in API order, with an independent View all suggestions/Show less control for the rest. These suggestions have no chronological history. Suggestions do not change balances.
- The record creator or a household owner/admin may edit or void a confirmed expense or bill. The web detail shows a "Remove mistaken expense/bill" action for this correction. The web flow requires a reason, a fresh API preview of the balance or pending-bill effect, and explicit confirmation. Editing payer, amount, participants, or split rules also requires a fresh API-calculated preview. A stale record or expired preview requires another preview. A voided record remains visible with actor, time, and reason, but cannot be edited or have its bill status changed. Its shares no longer affect balances; voided Unpaid bills leave pending totals. Recorded settlements remain unchanged. Store before and after versions of edits and voids for history. An unconfirmed web form may be discarded without creating a financial record.
- Every active household member may read a financial record's history on its expense or bill detail. Show creation, edits, bill provider-status changes, and voids with who acted and when. An edit shows changed fields with old and new values, including split inputs and final shares. Keep reported transfers and their recorder, transfer date, and recorded time in Balances. Only the creator or a household owner/admin sees edit and void actions; the API enforces those permissions and household isolation for every request.
- Let either the sender or recipient record a manual settlement after money has moved outside HouseMate. They review an API-calculated balance preview, then confirm the sender, recipient, amount, transfer date, and optional note or method. A custom amount is allowed with a warning if it exceeds the suggested amount. Show who recorded the transfer and when, and refresh balances after confirmation. A recorded settlement is a member's report, not proof that a payment provider completed or verified a transfer.

### Shared household life

- Board uses the shared page-header style: “SHARED UPDATES, PLANS TOGETHER”, the Board title, and “Share announcements, plan events, and see who’s joining.”

- Chores, shopping, meals and polls are removed from primary House navigation, creation shortcuts, web search filters and All records search results. Existing records, APIs, notification history, saved drafts and direct links are preserved. Notification settings hides their switches until explicitly expanded and never silently changes stored preferences. Assistant no longer promotes meal planning or these tools in its default copy/shortcuts, but existing read-only sources remain accessible. Assistant no longer offers action commands or action-draft recovery. Complete removal of the underlying modules is a separate product change.
- The Board tab (formerly House) opens on Announcements with only Announcements and Events navigation. Remove the shared Add menu and Your next actions panel. One create action sits beside the Board title and follows the selected tab: + New on phones, New announcement/New event on larger screens. Opening it focuses and scrolls to the form without clearing an existing draft; Cancel is inside the form. An accessible refresh control sits beside the list update status. Section headings are not repeated and there is no empty detail panel. Record filters have spacing below the section tabs. Filters remain on one horizontal row with scrolling on narrow screens or enlarged text; To acknowledge is the compact visible label for Needs acknowledgement, keeping the full acknowledgement meaning in its accessible name. Announcement rows show title, a two-line message preview, author/date, relevant priority/expiry and an Acknowledgement needed badge only when the viewer can acknowledge. Among loaded records, active urgent/important notices precede ordinary notices; within each priority newest appears first. API pagination remains newest-first. Events default to Upcoming with a Past filter and show date/time, title and attendance count. Selecting a record focuses its detail on small screens with a Back control. Event attendance and Add expense from event remain inside detail. Existing creation review/confirmation, draft recovery and authorization remain in force.
- Any active household member can publish a meal check with a type (breakfast, lunch, dinner, or other), question, meal time, response deadline, and selected active participants. Times are entered in the household timezone; the deadline must be in the future and before the meal. Each selected member can answer joining, not joining, or maybe, and change their own answer until the deadline. Responses lock at the deadline. Show each member's answer and counts for every state, including awaiting an answer.
- Any active member can assign short custom cooking roles, such as Cook or Helper, to selected active participants. Show the cooking plan on the meal detail. Existing meal records remain reachable through saved links and search.
- Any active household member may add and edit an open shopping item, assign an active member as buyer, cancel an open item, or mark it purchased. An item can record a name, optional quantity and unit, priority, note, estimated price, and actual purchased price. Unassigned open items are Needed; assigned open items are Assigned. Purchased and Cancelled items remain visible and cannot be edited or changed to another status in this release. A stale item revision must be refreshed before a change.
- Marking an item Purchased can optionally create a shared expense. The member enters the actual price, chooses the payer and split participants, selects a split method, reviews the normal API-calculated expense preview, and explicitly confirms. The member who marks it purchased is the default payer, but can choose another active member. Purchase and expense confirmation happen in one API transaction and the item links to the expense. A retry with the same confirmation key returns the same expense. Marking Purchased without an expense does not change balances. Prices use integer minor units with an explicit item currency; the first saved shopping price locks the household currency so old prices cannot change meaning. The home dashboard shows a live count of Needed and Assigned shopping items.
- Any active member may create a one-off chore with a title, optional note, due date and time in the household timezone, and one active assignee. Members see chores assigned to them, upcoming chores, overdue chores, and completed or skipped history. The assignee or an owner/admin can complete or skip an open chore; skipping requires a reason. An owner/admin can directly reassign an open chore.
- The assignee may request a swap with another active member. The requested member may accept or decline; accepting reassigns the chore. Only one request may be pending for a chore. Completing, skipping, or direct reassignment cancels a pending request. Stale revisions must be refreshed before a change. Home shows live open and overdue counts and the next due chore.
- Any active household member may create a future event with a title, optional details and location, and a start and optional end time in the household timezone. Members can browse upcoming and past events and see every current active member's attendance as Going, Maybe, Not going, or Awaiting. Each member may set or change only their own response until the event starts; responses then close. Event creation is safe to retry with the same key, and all reads and writes require active membership in the selected household.
- From an event, a member may start an expense draft with the event title and current Going members suggested as participants. If nobody is Going, the draft requires the member to select participants. The suggestion remains editable; payer, amount, date, split, and participants all go through the normal API-calculated expense preview and explicit confirmation. This first version does not persist an event-expense link or automatically change confirmed expenses when attendance changes.
- Any active member may publish an announcement with a title, message, Normal/Important/Urgent priority, selected active recipients, optional acknowledgement request, and optional future expiry in the household timezone. Review the draft before publishing. Publication is safe to retry; content and recipients stay fixed after publication. Selected active recipients, the author, and active owners/admins can read targeted records. Members acknowledge only as themselves; repeated acknowledgement requests retain the original timestamp. New acknowledgements close at expiry. Show recipient acknowledgement state and counts; departed recipients retain their recorded acknowledgement but do not count as actively awaiting. Browse All, Needs your acknowledgement, and Expired views.
- Any active member may publish a poll with a question, 2–10 distinct choices, single or multiple selection, selected eligible active voters, and a required future deadline in the household timezone. Review before publishing; question, choices, eligibility, and deadline stay fixed afterward. Selected active voters, the author, and active owners/admins may read aggregate results and their own saved selection. Only eligible active members may vote as themselves before the deadline. Saving replaces that member's entire selection atomically; retries never add another vote, and an empty selection withdraws it. Reject duplicate choices and option IDs belonging to another poll. Previous votes remain counted if a member leaves. Show option counts, distinct respondents, eligibility counts, and the deadline; multiple-choice percentages use respondent count and may sum beyond 100%. Browse Open, Needs your vote, and Closed views. Results refresh through the API about every 15 seconds while the section is visible and on return; preserve unsaved choices during refresh. This release has aggregate visible results rather than an anonymous-ballot mode.
- Deliver relevant activity and reminders through the personal notification feed described below. Mobile push remains planned for the mobile client.

### Notifications and reminders

- While the signed-in web app is open, new unread announcements, chore assignments/reassignments, and added shopping tasks show a brief popup from the selected household's authorized recipient feed, respecting the member's current In app category preferences. The first feed load establishes a quiet baseline; older entries are not replayed. The existing visible/online refresh detects updates roughly every 30 seconds and on return. Show at most three popups, with overflow available in the inbox. Each has View and Dismiss controls, closes after eight seconds, and pauses dismissal during hover, keyboard focus, or a hidden tab. It never takes focus automatically. Dismissal does not mark a notification read. Popups sit at the top-right on desktop and above phone navigation with safe-area spacing. Account/household-scoped timestamp and ID metadata in tab memory prevent duplicates across route changes; feed content and tokens are not persisted for this feature. Switching account/household discards visible popups and pending responses; access failures clear them. Quiet hours continue to apply to push delivery only. These in-app popups require neither browser notification permission nor live push setup.
- The header bell shows the selected household's unread count and opens Notifications. Browse All or Unread, load older entries with stable cursor pagination, mark individual entries read, or mark all entries through the newest displayed item read. Links open the exact related money or House record, whose API checks access again. Read state belongs to the recipient; another member cannot change it. Temporary refresh errors mark the retained view as possibly out of date; access failures clear it. Refresh while visible roughly every 30 seconds and on focus or reconnection.
- Notifications uses compact Inbox/Settings navigation. Inbox rows are grouped as Today, Yesterday and Earlier in the household timezone, with category icons, previews, unread dots and only Important/Urgent priority badges. The main row opens its source; a separate accessible action marks it read. Empty inboxes show the house mascot. Settings contains Device notifications, Choose updates and Quiet hours. Device management and category/channel switches expand on demand; quiet-hour times appear when enabled. Device controls apply to the account; category/quiet-hour preferences apply to the household. Preferences require explicit Save changes, with unsaved-change protection when leaving Settings. Checking devices preserves unsaved preference edits, and unavailable/blocked device status is shown explicitly rather than treated as enabled.
- New expense/bill creations, revisions and voids, manual transfers, selected meal invitations and cooking roles, chore assignments/status and swap requests, shopping changes, events, targeted announcements, and eligible polls create recipient entries in the same transaction as the action. Active household membership is required to read the feed. Targeted communications are sent only to selected recipients/voters, transfers to their two participants, and assignments to the relevant members. Existing activity is not backfilled; unresolved deadlines can produce reminders after the worker starts.
- The API generates reminders about once per minute while running on a persistent host, or through a configured minute-level scheduler on serverless hosts. Vercel Hobby uses an external scheduler calling a secret-protected API job; it does not run a persistent background timer. Reminder timing depends on successful scheduler runs, so production requires scheduler setup and monitoring. Bills notify share participants within two household calendar days of due date, on the due date, and once overdue, using only the nearest phase at each check. Unanswered meals and unvoted polls get one reminder within an hour of closure; open assigned chores get one within a day and one overdue; upcoming events get one within a day for Going, Maybe, or unanswered members; expiring announcements get one within a day for recipients still needing acknowledgement. Deterministic keys prevent repeated reminders for the same phase. Completed, answered, paid, expired, or otherwise irrelevant items are rechecked before push delivery.
- Each member chooses In app and Web push independently for Expenses, Bills, Settlements, Meals, Chores, Shopping, Events, Announcements, and Polls in each household. All in-app categories are initially on; Shopping push is initially off. Muting affects future feed entries and leaves existing history available. Push requires an enabled browser device and is also checked against current preferences before sending.
- Optional quiet hours use the household timezone, support overnight windows, and delay every push priority until the window ends. They do not hide the inbox. Defaults suggest 23:00–07:00 with quiet hours initially disabled. A delayed reminder is skipped if it has expired, been answered, or been read.
- Web push is explicit opt-in after an explanation of its value and privacy. Do not open a permission request automatically. Show instructions for browser denial or unsupported platforms. Devices belong to the account across households, with up to ten active devices; members can disable them, and signing out removes the current browser subscription. Refresh an existing subscription on a signed-in visit; missing subscriptions require explicit Enable again, and remote-disabled devices are never silently re-enabled. Expired provider subscriptions are disabled; transient errors have bounded retries.
- Lock-screen title and body are generic: no financial amounts, household names, or private message text. Push links stay on the app origin and require authentication and authorized household access. Newly enabled devices receive only subsequent updates. Provider acceptance can be ambiguous during retries; notification tags coalesce duplicate deliveries, but device delivery is not guaranteed.
- Live web push requires a real server contact email or HTTPS support URL, server-only VAPID private key, and a supported secure browser context. Until configured, the inbox, reminder generation, and preferences work and the web screen explains why push is unavailable. Production requires HTTPS; some mobile browsers require an installed PWA. Production VAPID/contact configuration was activated on 2026-10-02; each member must still explicitly enable each device, and real-device delivery acceptance remains separate from server activation. Notification taps ask the browser to open the same-origin source link in its app context, focus the returned window, and recover through a live app window if opening fails. Unsupported links open Notifications. Browsers determine whether an installed app or browser window is used; normal session and API authorization remain required. Native mobile push, email, SMS, and LINE delivery are not implemented in this slice.

### Web and mobile experience

- Provide the essential household workflows in both the responsive web app and the iOS/Android mobile app. Layout and platform controls may differ, but confirmed financial results must match.
- Clearly distinguish loading, empty, error, draft, pending, and confirmed states. A financial action is final only after the API confirms it.
- Make common flows usable with accessible labels, keyboard support on web, and meaningful notification deep links.

### Appearance and account menu

Signed-out visitors at the root see a public landing page with shared-money,
daily-coordination and household-updates features, setup steps, an interactive
product tour, FAQ and a factual privacy overview. Product illustrations use
explicitly labelled fictional records. Get started/Sign in open `/sign-in`;
the root waits for session restoration and browser launch detection with the mascot and “Opening HouseMate…” before selecting a screen. Restored members continue directly to their dashboard, without a landing-page flash. Signed-out Home Screen launches on Android Chrome and iPhone Safari open sign-in instead of marketing. Invite/household deep links and
authentication callbacks bypass marketing and preserve the normal access flow.
Landing content supports light/dark mode, keyboard controls and phone layouts.
The public page is divided into Overview, Features, How it works, Tour, Privacy
and FAQ along the natural vertical scroll. Fade each upcoming section in as it
enters view, then keep it visible. Header anchors jump directly to sections;
there are no Next/Previous controls, progress counters or forced scroll snapping.
Reduced motion, unavailable animation APIs and keyboard focus keep content
visible. All sections remain in the document/accessibility flow, grow on small
screens. The root entry requires JavaScript to finish the session/launch check; public landing content is then shown only to signed-out browser visitors.

Web provides a light/dark toggle beside the header profile icon and on sign-in.
Initially it follows the device preference, then remembers an explicit choice
locally across visits/tabs. The profile icon opens the current account, Profile,
Switch Google account and Sign out. Google switching prompts for account selection
using the configured provider and retains the current session until completion.
Members must finish or discard open drafts before switching or signing out.
Account changes replace household UI state and request the new account's authorized
data. One browser has one active session shared across tabs; switching does not
merge users, memberships or financial records.

### Interaction motion

- Use brief content fades for main tab changes while shared navigation stays mounted. Buttons give subtle press feedback; transitions never delay routing or confirmation controls.
- Keep Assistant thinking dots inside the question box, add one short mascot greeting per Assistant visit, and fade in new answers. General/household answer content and money amounts remain unchanged.
- Search and household menus fade on desktop; phone search/household sheets slide up briefly, retaining focus trapping, keyboard and safe-area behavior. View all/Show less previews use a short content fade in place; avoid animating container heights or counting through money values.
- Show an animated decorative check only alongside verified successful saves, acknowledgements, attendance and confirmed record actions. Pending, uncertain and failed confirmations keep their existing state and cannot trigger success feedback.
- New notification popups slide/fade in. Dismissal makes a popup inert and unavailable to accessibility APIs immediately, then removes its visual exit after 160 ms. Reduced motion removes it immediately. Existing pause-on-hover/focus/hidden behavior, unread state and scope cleanup remain.
- Honor the OS Reduce motion preference. New transitions use lightweight CSS, opacity and transforms with mostly 150–200 ms durations, no animation library, no background network work and no delayed writes.

### First-release web quality

- Keep the authenticated app shell mounted across Home, Money, Board, Assistant, Profile and Notifications navigation. Retain the loaded account view and shared header/navigation controls within the current account and household; synchronize household selectors and exact record links with route changes.
- On returning to Home, Money or Board, show an available authorized read snapshot from this browser tab for up to 60 seconds while requesting fresh API data. Snapshots live only in bounded browser memory (64 responses), keyed by session and household; they are not persistent storage or an offline data source. Show a last-checked/updating status and an outdated warning after refresh failures. Clear retained data on access rejection and invalidate snapshots after household writes, account/session changes and household changes. Responses started before invalidation cannot repopulate snapshots.
- Snapshot reuse covers dashboard, balances, members and first-page expense/bill/settlement/announcement/event reads only. Details, later pages, search, Assistant responses and financial previews/confirmations always use fresh API requests. Keep explicit confirmation and existing draft guards. Show accessible section-shaped loading placeholders when no recent snapshot exists; actual phone performance must be measured separately.

- Prioritize Android Chrome and iPhone Safari. Offer installation help on sign-in and Profile, an explicit browser install action when available, home-screen icons, and safe-area spacing. Installation and notification permission are separate choices.
- Cache only a public offline navigation screen. Never cache private household/API responses in the service worker or queue household writes. Existing displayed data may be stale offline; show a connection notice. Reconnection refreshes reads on return and never resubmits a financial action automatically.
- A disconnected, timed-out, or unreadable financial confirmation reply is **Not yet confirmed**: the server may already have saved it. Retain the current draft, preview, and confirmation key for an explicit retry. A request rejected locally because the browser is offline is clearly identified as not sent. Structural accessibility and palette checks supplement manual screen-reader, keyboard, 200% zoom, and phone acceptance checks; automated results alone are not accessibility certification.

### Automatically saved drafts

- Automatically save editable new-expense, bill, meal, shopping, chore, event, announcement and poll fields in browser storage on this device. One slot per account, household and form type is kept for seven days since the last save. Returning to that form offers Resume draft and Discard saved draft; recovery makes no household write. Draft status explains whether saving succeeded or browser storage is unavailable. These are private local entries, not live household records or synchronized backups.
- Restore only under the same signed-in account and an authorized household. Account changes/sign-out clear saved drafts. The current household list prunes departed households; currency/timezone changes invalidate that household's draft context. Explicit cancel/discard and a verified successful submission remove the saved entry. Another tab cannot silently overwrite an entry changed since it was read; warn and require reloading/reviewing instead. Invalid, expired, oversized or unsupported saved data is discarded safely.
- Persist explicit editable fields and retry metadata only. Do not persist session tokens, AI answers, API record/member snapshots or API-calculated preview totals. Assistant input is excluded from persistent recovery; old saved questions/action seeds are ignored. Gemini acknowledgement and chat answers are not restored. Local storage is not encrypted by HouseMate and may be inspected by someone with access to the browser profile; clearing site data removes drafts.
- Financial recovery returns to editing and requires a fresh normal API preview before explicit confirmation. Before a create request, retain its original editable fields, exact payload signature and idempotency key. An unresolved confirmation can only be retried with the same payload/key; changing fields cannot create another copy. A definitive first-attempt rejection permits correction. Neither refresh, reconnection nor recovery automatically sends a write. A member must check an uncertain result before deliberately discarding it.
- This release recovers new-record drafts, not Assistant questions or existing-record edits, shopping purchase confirmations, settlement/removal drafts, settings or unsaved votes. Their existing leave/update guards remain. Storage denial, quota limits, clearing browser data and an abrupt shutdown before the browser commits a save can prevent recovery. Phone/browser acceptance must include a refresh, full app restart, reconnect and interrupted confirmation.

## Currency behavior

- Support **USD** and **Thai baht (THB)**. Each household chooses one currency, either USD or THB, and all its financial records and totals use that currency.
- Display amounts with two decimal places and a clear currency label. Store and calculate cents or satang precisely so every split allocates the full original amount.
- Do not combine USD and THB in one balance or convert between them in the first release.
- Once a household has financial activity, changing its currency is unsupported in the first release; historical amounts must not silently change meaning.
- The electricity example in `MONEY_ENGINE.md` is a product acceptance scenario for hybrid bills.
